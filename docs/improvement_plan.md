# План улучшения Story Forecaster

Дата: 20 сентября 2026. Основание: `project_audit_2026-09-20.md` и обсуждение режима написания фанфика.

## Цель и границы

Сначала получить воспроизводимый прогноз по реальным данным с проверяемыми источниками и честными метриками. Затем использовать этот фундамент для написания и редактирования продолжения в отдельной сюжетной ветке.

Это план работ, а не отчёт о выполнении. Реализация приложения, переиндексация книг, изменение БД и обращения к платному API в рамках подготовки плана не выполняются.

Сохранить Python, FastAPI, SQLAlchemy, SQLite, существующие доменные модели и простой frontend. Исправлять проект последовательными законченными изменениями. Каждый этап заканчивается демонстрируемым результатом и проверкой критериев приёмки. Исходное ТЗ сохраняется; этот документ задаёт порядок восстановления и развития реализации.

Не читать и не переобрабатывать NB* целиком для исправления инфраструктуры. Использовать синтетические примеры и метаданные. Для будущего содержательного пилота отдельно определить небольшой разрешённый набор фрагментов и лимит расходов; не считать этот план разрешением на массовую обработку корпуса.

## Порядок

`M0: достоверность и запуск → M1: версии и источники → M2: реальный baseline → M3: память и retrieval → M4: оценка и эксперименты → M5: канон и автор → M6: написание сцен → M7: длинные арки и эксплуатация`

Канон и авторские прецеденты не блокируют первый реальный прогноз. Режим писателя не обязан точно угадывать оригинал, но требует корректных источников, памяти и проверки противоречий. Низкая точность прогнозирования — допустимый исследовательский результат, а не основание подменять метрики.

## M0. Сделать приложение честным и воспроизводимым

**Результат:** проект устанавливается с нуля, демонстрационный режим явно обозначен, тесты не затрагивают пользовательскую БД.

- Добавить `pyproject.toml`, воспроизводимое описание зависимостей, установку src-пакета и команды запуска в README. Проверить чистую установку в отдельном окружении.
- Подключить единый валидируемый загрузчик конфигурации; настройки провайдера, таймаутов, повторов и лимитов должны реально применяться.
- Разделить `demo` и `real` в CLI/API/UI и сохраняемых прогонах. Выбор провайдера должен соблюдаться; недоступность реального провайдера возвращает явную ошибку.
- Убрать безусловные continuity_verified, topology=100%, вероятность 80% и заявления о доказанной изоляции. Абляционные константы оставить только как явно синтетическую fixture вне рабочих метрик.
- Исправить endpoint памяти и поля авторских правил во frontend. Значение cutoff_chapter должно быть номером главы, а не сцены.
- Выводить текстовые значения через безопасные DOM-операции. Ограничить допустимые числовые параметры API. Для текущего локального UI использовать same-origin.
- Перевести тесты на временную БД и синтетические данные. Исправить тесты, закрепляющие ошибочное поведение.
- Сделать doctor информативным: отдельные статусы БД/корпуса/конфигурации, ненулевой exit code при обязательном сбое; сетевой probe не имитировать наличием ключа.
- Убрать автоматическую генерацию при открытии страницы, чтобы просмотр интерфейса не создавал прогоны и расходы.

**Файлы:** `providers/`, `api/main.py`, `cli.py`, `domain/forecast.py`, `frontend/`, `backend/tests/`, `config/`, README и runbook.

**Приёмка:** чистая установка и demo работают по инструкции; suite работает без реальных книг и API; тестовые запуски не меняют рабочую БД; UI не выдаёт фикстуры за реальные измерения.

## M1. Исправить версии, границы и происхождение данных

**Результат:** любой анализ относится к точному произведению, неизменяемой версии и разрешённой границе.

- Перед миграцией создать резервную копию SQLite и проверить восстановление на отдельной копии. Не удалять старые версии как «дубли» автоматически.
- Ввести общий resolver `project → work → version → chapter → cutoff_seq`; API и CLI используют одну реализацию.
- Во всех запросах ограничивать проект и версию. Передавать work_version.id, а не work.id. Не выбирать главу глобально через ordinal + first().
- Сделать ForecastScope неизменяемым, валидировать границы, включить все параметры политики/разрешённых manifest в его канонический хеш.
- Не полагаться на хеш как на проверку доступа: каждый источник отдельно проверять по версии, разрешённому manifest и, для исторического режима, времени доступности.
- Ввести минимальную адресацию свидетельства: версия источника, глава/сцена, точные символьные границы и хеш фрагмента. Разделители учитывать по реальным позициям, а не фиксированным прибавкам.
- Повторный импорт одинаковых данных сделать идемпотентным. Исправление или дополнение произведения создаёт новую версию; старые результаты остаются привязаны к прежней.
- Для updater определить отдельные операции append и revise. Исправление ранней главы не переносит её сцены в конец последовательности.
- Включить контроль FK на SQLite-соединениях, добавить необходимые индексы и уникальность номеров в пределах родительской сущности. Миграции должны сохранять существующие данные.
- Производные артефакты хранить с зависимостями от входов и статусом актуальности. Не переиспользовать кеш после изменения источника или политики.
- Счётчики manifest/БД рассчитывать единообразно; обозначить, включают ли символы заголовки и нормализацию.

**Файлы:** `domain/scope.py`, `db/`, `ingestion/`, `retrieval/engine.py`, API и CLI; небольшие общие модули policy/evidence добавлять по фактической необходимости.

**Приёмка:** синтетические два проекта и две версии не смешиваются; повторный импорт не размножает данные; корректировка главы сохраняет историческую версию; spans восстанавливают точный фрагмент; недопустимый источник блокируется до вызова модели.

## M2. Получить первый настоящий прогноз без ручных сюжетных ответов

**Результат:** прогноз строится на явно сохранённом контексте через реальный провайдер.

- Начать с простой конфигурации: разрешённые последние сцены и явно обозначенные исходные ограничения → один запрос → 3 различающихся кандидата. Ручную память текущей книги пока не использовать как подтверждённые факты.
- Передавать модели фактический контекст и поддерживаемую схему ответа, а не только имя Pydantic-класса. Валидировать результат локально.
- Ввести сборку контекста с лимитом объёма; возвращать список включённых источников и сведения об усечении. Текст источников отделять от управляющих инструкций.
- Проверять идентификаторы ссылок: модель может ссылаться только на реально переданные разрешённые источники. Не принимать выдуманные цитаты.
- Записывать Run со статусами queued/running/completed/failed, моделью, настройками, версией промпта, входным manifest, фактическим запросом/ответом и доступными usage-полями. Не сохранять секреты.
- Сохранять полный объект кандидата. Ошибка сохранения не должна выглядеть как полностью успешный сохранённый запуск.
- Добавить ограниченные таймауты/повторы и лимит числа запросов. Перед содержательным пилотом определить бюджет и проверить выбранную модель по актуальной официальной документации.
- Не обещать побитово одинаковый ответ при повторном вызове внешней модели: воспроизводимость означает возможность восстановить входы, параметры и сохранённый результат.

**Файлы:** `providers/gemini.py`, `providers/base.py`, `forecast/engine.py`, `domain/forecast.py`, `db/models.py`, новые версии промптов.

**Приёмка:** тест-перехватчик подтверждает передачу контекста и схемы; недоступный провайдер не превращается в demo; некорректные ссылки отклоняются; небольшой реальный пилот сохраняет полный прогон и фактические расходы/usage, если доступны. Без ключа этап отмечается как инженерно проверенный, но не проверенный на live API.

## M3. Реализовать настоящую память и подключить поиск

**Результат:** состояние на главе N вычисляется из допустимых свидетельств, а найденные сцены участвуют в генерации.

- Заменить фиксированные карточки персонажей и сюжетные линии извлечёнными/размеченными записями со ссылками на источники.
- Разделять наблюдаемые события, утверждения рассказчика, реплики персонажей, убеждения, предположения и неизвестность. Реплика не становится автоматически фактом мира.
- Хранить момент доступности факта читателю отдельно от времени события внутри истории. Для флешбэков и раскрытия тайн отсечка действует по доступности читателю.
- LLM-экстрактор предлагает структурированные записи; валидатор проверяет ссылки и форму; reducer детерминированно строит snapshot и сохраняет конфликты свидетельств.
- Ввести версии знаний/состояний и событийные изменения вместо редактирования одной финальной карточки. Snapshot на N не включает обновления из N+1.
- Подключить BM25 к ContextBuilder. Запросы строить из текущих целей и открытых линий, а не фиксированного списка сюжетных тегов.
- Разделить смысловые сцены и ограниченные по размеру поисковые chunks с точными координатами.
- Измерить пропуски из-за русских словоформ. Улучшать нормализацию по найденным ошибкам. Текущий token overlap честно назвать лексическим, не dense.
- Кешировать поиск по версии/границе/политике; статистика индекса в историческом режиме не должна учитывать закрытое будущее.

**Файлы:** `memory/engine.py`, `domain/memory.py`, `retrieval/`, `forecast/engine.py`, таблицы событий/утверждений/свидетельств по минимальной необходимой схеме.

**Приёмка:** поздний персонаж и его имущество отсутствуют в раннем snapshot; изменение поздней сцены не меняет ранний контекст; противоречие не теряется; retrieval отдаёт нужное свидетельство из правильной версии; ContextBuilder действительно включает его в запрос.

## M4. Сделать оценку пригодной для решений

**Результат:** метрики пересчитываются из реальных прогонов и не награждают противоположные события.

- Отделить данные gold и оценщик от доступных предиктору источников. Зафиксировать небольшой набор точек отсечки, материал для настройки и закрытый финальный набор.
- Размечать атомарные события: участники, действие, объект, исход, отрицание/модальность и важные причинные связи. Не менять критерии под уже полученные ответы.
- Добавить негативные примеры: уничтожение вместо создания, другой участник, только упоминание предмета, отрицание события, предполагаемое вместо случившегося.
- Исправить веса совпадений; проверить их на ручной разметке. Если используется LLM-оценщик, фиксировать его версию/рубрику и отдельно проверять согласие с человеком.
- Обеспечить 1-to-1 сопоставление с максимальным общим весом. Отдельно показывать совпадения, пропуски и лишние события.
- Убрать константные consistency/topology. Непроверенное обозначать not_checked. Ранжирование кандидатов фиксировать до открытия gold.
- Реализовать запуск конфигураций: B0 — недавний контекст; B1 — +память; B2 — +поиск. После M5 — +канон и +автор, а также отключение каждого из них из полной системы.
- Сравнивать на одинаковых точках отсечки, модели и сопоставимых бюджетах. Сохранять повторные прогоны и разброс, а не только лучший результат.
- Публиковать Best@1, Oracle@K, противоречия, разнообразие, retrieval recall, задержку и стоимость отдельно. На малом наборе показывать каждую главу.
- Сохранить прогноз будущей неопубликованной главы до её выхода как отдельный перспективный эксперимент. Ретроспективная отсечка не устраняет возможное знание книги самой моделью.

**Файлы:** `evaluation/`, тестовые fixtures, журналы экспериментов, README.

**Приёмка:** пример «Куб уничтожен» не получает полного совпадения с крафтом; каждая строка benchmark имеет run IDs и пересчитывается; real/demo разделены; ухудшение расширенной системы отображается без подмены результата.

## M5. Добавить проверяемые канон и авторские прецеденты

**Результат:** дополнительный контекст имеет источники и измеренную пользу.

- Версионировать канонические источники и overlays; отличать первоисточник, изменение фанфика и предположение. Не переносить знания читателя в знания персонажа.
- Для прецедента хранить подтверждённые ситуацию, решение и последствие с координатами источников. Regex использовать только для поиска кандидатов на разметку.
- Согласовать словарь тегов, исключить случайные подстрочные совпадения, добавить дедупликацию и соблюдение разрешённого manifest.
- Начать с небольшой выборки; учитывать альтернативные исходы. Не превращать частоту в некалиброванную «вероятность автора».
- Реально включить выбранные прецеденты и canon overlays в ContextBuilder. Показывать, что попало в запрос и почему.
- Через M4 проверить вклад каждого компонента. Сложные компоненты оставить опциональными, если улучшения не обнаружены.
- Embeddings и reranker добавлять только после измеренного недостатка лексического поиска и с отдельной проверкой границ.

**Приёмка:** каждый использованный прецедент можно открыть в разрешённом источнике; повторный индекс не размножает записи; отключение компонента меняет фактический контекст; вывод о пользе основан на сохранённых измерениях.

## M6. Добавить режим написания фанфика

**Результат:** система пишет, проверяет и редактирует сцены в отдельной ветке, не изменяя оригинал.

- Создавать Branch от точной версии и отсечки. Хранить принятые изменения ветки отдельно от исходных событий, черновиков и прогнозных кандидатов.
- Ввести ScenePlan: цель, POV, участники, исходное состояние, известные им сведения, конфликт, обязательные биты, допустимые изменения и желаемый исход.
- Добавить речевые профили: словарь, длина реплик, манера общения, различия в зависимости от собеседника; хранить основания или явную пометку авторской настройки.
- Scene Prose Synthesizer получает план, релевантный контекст и ограничения. Длину сцены задавать по функции и темпу, не растягивать каждый бит до фиксированного числа слов.
- Отдельно проверять исполнение плана, POV, знания, временную последовательность, ресурсы, травмы и позиции персонажей. Художественную редактуру отделить от проверки фактов.
- После черновика извлекать ProposedStateDelta со ссылками на фрагменты сцены. Не записывать её сразу в основную память.
- В первом MVP пользователь принимает/редактирует сцену; валидатор проверяет delta, затем транзакционно фиксируются AcceptedScene и изменения состояния ветки. Для черновиков использовать draft/rejected, не «факт».
- При правке принятой сцены создавать новую ревизию, пересчитывать затронутые snapshots, помечать зависимые продолжения требующими проверки. Поддержать откат и альтернативную ветку.
- Художественное продолжение в UI должно приходить из сохранённой генерации, а не константы JavaScript.

**Предлагаемые компоненты:** `writing/` для планов, прозы и редакторского цикла; `branches/` либо соответствующий сервис над БД. Существующие memory/retrieval/provider переиспользовать.

**Приёмка:** 3–5 последовательных сцен на синтетическом сюжете проходят весь цикл; отклонённая сцена не меняет память; ложь в диалоге не становится фактом; отмена ранения убирает его из последующих snapshots; оригинальная книга не изменяется; принятый текст экспортируется в Markdown/TXT.

## M7. Проверить длинные арки и улучшить рабочий интерфейс

**Результат:** удобная работа над несколькими главами и измеримые ограничения качества.

- Ввести планы арок и глав: цели, этапы, обещания читателю, загадки, подготовка и развязки. Отличать будущий план от уже произошедшего события.
- Отслеживать незакрытые обязательства, возраст линии, повторение конфликтов и незапланированные отклонения. Изменение плана явно версионировать.
- После принятия главы выполнять редакторскую проверку темпа, повторов, голосов и причинной связности с предыдущими главами.
- Интерфейс: динамический выбор версии/отсечки/ветки, источники, сравнение кандидатов, diff изменений состояния, история, откат, ошибки и действительные статусы проверок.
- Для длительных задач добавить простую сохраняемую очередь/worker с отменой, прогрессом, лимитом расходов и восстановлением. Не вводить распределённую инфраструктуру без необходимости.
- Провести сначала пилот на 3–5 главах, затем более длинный. Оценивать на разных участках истории число противоречий, забытых линий, повторов и объём ручной правки, а также художественную оценку по фиксированной рубрике.

**Приёмка:** есть журнал качества по главам и затратам; длинный прогон можно остановить/продолжить; вывод «качество сохраняется» допускается только в пределах измеренного пилота, без обещания отсутствия деградации вообще.

## Первые пять законченных изменений

## Финальные условия готовности

**Прогнозировщик:** устанавливается с нуля; использует реальный разрешённый контекст; не смешивает версии; хранит свидетельства и полные прогоны; честно сравнивается с baseline. Успех инженерной реализации не выдаётся за доказанную высокую точность.

**Писатель:** планирует и генерирует сцены; предлагает и проверяет изменения состояния; фиксирует только принятый текст в отдельной ветке; поддерживает ревизии и откат; оценивается по связности и художественному качеству отдельно от совпадения с оригиналом.
